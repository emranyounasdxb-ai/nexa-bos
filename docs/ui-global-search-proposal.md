# Header global search — proposal awaiting owner review

Global search is a new feature. Neither the current header nor inspected earlier header revisions implement it. Figma headers 90:3 and 296:159 show a search presentation, but do not establish result behavior. No search control, endpoint, dependency, database change or search architecture has been implemented in this correction.

## Recommended first release

Search authorized navigation destinations plus four existing record types through their existing, paginated APIs. Every URL below is an existing route. Backend authentication, permissions and record visibility remain authoritative; client provider selection only avoids unnecessary requests.

| Record type | Existing API and matching fields | Authorization / visibility | Open result |
| --- | --- | --- | --- |
| Applications / cases | `GET /api/v1/applications?q=…&page=1&page_size=10`: application code, bank case number, customer code/name/company/mobile, bank/product/variant code/name | `Applications.View`; `visible_case_owner_ids` applies the current own/office/hierarchy/company scope. TL scope includes self and directly assigned same-team/office/department SEs. | `/applications/{id}` |
| Customers | `GET /api/v1/customers?q=…&page=1&page_size=10`: customer code, personal/company name, mobile, email, historical identifiers | `Customers.View` **and OWNER/GM role**; the service also filters visible customer IDs. Other roles must not get a standalone customer-directory provider. Their authorized cases can still match customer information through the application API. | `/customers/{id}` |
| People / users | `GET /api/v1/users?q=…&page=1&page_size=10`: name, user/employee code, email/mobile, office/department/team/designation | `Users.View`; `visible_user_ids` enforces the current scope, including TL's narrower team rule. Header destinations must also follow the existing role restrictions: TL must not get links to the generic Users screen. | `/users/{id}` for roles with that existing destination |
| Assets | `GET /api/v1/assets?q=…&page=1&page_size=10`: asset code, brand/model, serial, IMEI/ICCID/mobile number | `Assets.View`; company/office scope or active allocations to visible users, enforced by `_visible_assets_stmt`. Respect existing role restrictions on the Assets destination. | `/assets/{id}` |

Display only record type, public-facing record code and existing name/title (asset brand/model). Do not render email, phone, identity history, financial amounts, nationality, salary, document contents, credentials or full API payloads in suggestions. A match on an existing searchable field does not authorize showing that field. Permission-denied/not-found providers must reveal neither restricted record counts nor identifiers. Opening a result retains the destination's existing authorization checks, including revoked access.

Navigation results can match the **already filtered** menu labels and their existing routes. Hide unauthorized destinations and empty sections exactly as the header does today; this adds discoverability across modules without searching their sensitive records.

## Other module findings and exclusions

- **Banks, products, variants:** existing `/api/v1/banks`, `/products`, `/product-variants` and `/bank-products` return authenticated master lists, without a text-query/paginated search contract. Inactive results require existing manage permissions. The app additionally uses `canReadCatalog` and excludes TL; the list APIs themselves use `CurrentUser`, rather than that same catalog-destination rule. Do not treat the client rule as a security boundary. Recommend deferring standalone catalog results: a later phase needs an explicitly approved server authorization rule, bounded query/pagination and a way to focus the selected record in `/catalog?tab=…`. No new endpoint is assumed. Applications already match their associated bank/product names safely within case scope.
- **Organization, hierarchy and unified Designations:** existing master APIs and `/api/v1/user-types` can supply permitted master records. Hierarchy supports `q` under `Users.View`, but returns a hierarchy response, rather than a bounded generic search provider. Master lists lack the same text-query/pagination contract and deep-link selection used by the proposed record types. Defer standalone records; preserve unified Designations and offer authorized page destinations only.
- **HR / PRO:** `/api/v1/employee-profiles/dashboards/pro` accepts a bounded `q` under `UserProfiles.PRO.View`, excludes TL and returns compliance information. It overlaps people search and introduces document-related disclosure concerns. Defer compliance/document results; do not infer HR visibility from `Users.View`.
- **TL dashboard:** `/api/v1/reports/tl-dashboard` has its own `search` and queue contract under `Dashboard.View`. Preserve it as the existing workspace search; do not fetch an entire dashboard to simulate a global provider. TL case details already have `/applications/{id}` routes.
- **Attendance, leave, contracts, transfers, exit/offboarding, approvals, targets/KPI, Finance, reports, notifications, workflows/case operations and Security:** reviewed route definitions expose module-specific filters, queues, aggregates or configuration, rather than a common bounded text-search contract with matching existing record deep links. These are not approved global record providers. Offer only authorized existing page destinations in the first release; do not search salary, approval payloads, security logs, attachments or aggregated metrics.

## Minimal implementation plan for approval

1. Approve the four record providers and navigation results above. Confirm deferral of standalone catalog/HR-document/other module records. The first-release placeholder must name the actual searchable types; Figma's product wording must not imply a standalone product provider.
2. Add a header search controller using the existing `apiGet` authentication/error handling and `RequestInit.signal`. Debounce typed input, cancel obsolete requests and discard stale responses. Query only enabled providers, with a minimum query length and the existing valid page size of 10; show a small bounded subset per type. Do not fetch every page or preload entire directories. No new dependency, endpoint, service, index or migration is needed for this first release.
3. Reuse existing dialog/input/loading/empty/error controls. On wide desktops, use Figma's search treatment where space allows; at narrower desktop/tablet/mobile widths, a search icon opens the same keyboard-accessible search dialog. Keep full-page menu centering and all existing utilities/actions available. Define result keyboard navigation, focus return, explicit close and per-provider failure states before implementation; this interaction is a proposed extension, not a direct Figma frame match.
4. Test real API search with a disposable, identity-verified database: authorized matches, unauthorized providers, own/office/company/hierarchy/TL boundaries, cross-scope record IDs, revoked permissions and session expiry. Verify record links and stale-request cancellation. Inspect rendered light/dark screenshots at desktop/tablet/mobile and intermediate widths, including the future utility-width change. No production data or persistent local database reset.
